No further trajectory features take priority over the industrial workflow.

Existing dispatch planning is in the legacy field-capabilities flow and is not yet fully integrated into the executable industrial runtime. Do not describe these as completed commercial capabilities.

Next implementation gates:
1. Versioned Machine Context: asset identity, OEM/model, retrofit kit/control software/harness/interface revisions, network topology and measurement endpoints, site/operating conditions, permissions and available diagnostic tools. Each known attribute needs source, effective time, recorded time and confirmation status; missing stays unknown. Run/check/decision records freeze the relevant context version. Comparability must use fault-specific required attributes and exclusions, never a blanket brand match.
2. Context-aware check candidates: specify competing fault domains, required/available/missing signals, expected discriminating observations, remote/onsite feasibility, personnel/tools, permissions, safety prerequisites, operational disruption and unknown cost/time. Rank separately for reducing uncertainty and restoring operations. Explain ordering from evidence and constraints; no uncalibrated information-gain or root-cause probabilities. Checks without required permissions/evidence are blocked or conditional, never silently executable.
3. Review/result lineage: retain proposed check + rule/version + context/run/evidence snapshot; accept/reject/edit requires an engineer reason; preserve original versus revised procedure, execution status, timestamps, actual observations and sources. A skipped or planned check is never an executed result. Capture whether new evidence changed domain priorities or dispatch preparation.
4. Dispatch/Outcome integration: remote unresolved items, prerequisites before dispatch, engineer-reported tools/parts preparation and exclusions; link actual intervention, recovery verification window, recurrence and resource/time observations. Preparation suggestions are not proof of a damaged component or dispatch approval.
5. Evaluation before specialized models: collect incident start/report, triage, decision, dispatch, arrival, intervention and verified recovery times with clock/source/unknown distinctions. Report observed durations first. Claim reduced handling time only against an explicit comparable baseline with case-mix/coverage limits. Chronological held-out cases and adjudicated labels are required before claiming model or memory benefit.

Until BuilderX confirms a bounded fault type and supplies authorized data, use clearly synthetic remote-delay inputs to validate mechanics. Do not assume supplied data, agreed pilot, labeled root causes or commercial effectiveness. Specialized learned policies come after stable auditable records and independent evaluation; they are not the immediate implementation target.

## Shared architecture
Adapters (CERBERUS TUM and explicit industrial CSV/JSON schema mapping) → hashed read-only sources and normalized samples → allowlisted numerical tools → immutable investigation runs + findings/hypotheses/checks → source-linked engineer feedback → append-only decisions/actions/outcomes → chronological context-qualified memory retrieval. Existing Field Case remains the container. No arbitrary generated Python, SQL, shell, source instructions or external model calls. Deterministic orchestration is operational with no LLM.

## Numeric validity and limits
TUM: strict increasing finite timestamps and unit quaternions; explicit frame labels; nearest timestamp association within an explicit tolerance, no extrapolation or fabricated synchronization. SE(3) rigid alignment is retrospective evaluation only, no scale fit; report transforms, pairs, temporal gaps and aligned versus raw residuals. No alignment against unknown frames without an explicitly chosen evaluation transform. Missing reference => metrics unavailable. CPU/data limits bounded; downsample plots only, compute full permitted subset. Original hashes and row indices link calculations to exact inputs.
